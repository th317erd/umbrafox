### Custom-code mechanisms worth isolating

The registry's global any-enabled flag reaches document ScriptLoader source and
stencil/bytecode cache guards independently of origin matching. No current measurement
quantifies its effect; this does not mean HTTP or all JIT caches are disabled.
The active document-start actor also blocks parsing on a parent query before
learning that an unrelated origin has no scripts.

After a matching document installs the process-global HTTP observer, eligible
requests can be suspended for an actor round trip before the child discovers
there are no request handlers. Publishing an empty script list does not undo
that observer registration. Fresh-none and previously-active-then-disabled are
therefore different source paths and need separate controls.

Controller WeakRef values do not retain the controller strongly, but numeric map
keys/wrappers can outlive it absent another lookup for that key. This is not proof
of a live-document leak or the owner's historical freeze cause. Measure lifecycle
and growth before a cleanup or fast-path repair.

### Measurement must account for its own effects

Detailed WR traces are still compiled in despite runtime gates. Existing profiler
start/stop can discard JIT code; GC enclosing intervals are not pause duration;
generic EGL `WaitForGPU` is a no-op in the inspected implementation. Styles/RDL
bookkeeping is not wholly absent when markers are disabled. These facts prohibit
zero-overhead or complete GPU-wait claims from gate names alone.

`searchfox-cli` works but advertises an update from 0.18.0 to 0.20.4. No tool or
system setting was updated during this foundation wave.

## Local execution runbook

Run from the repository root with existing Node and binary. Use a NEW output
directory each time. The runner creates and cleans its own browser process group,
profile and loopback HTTP service. It retains evidence and its disposable profile
directory; no claim that browser startup makes zero unrelated built-in requests.

```bash
timeout 120 node --test tools/umbrafox/performance/test/*-spec.mjs
timeout 150 node tools/umbrafox/performance/run.mjs \
  --binary /home/wyatt/Projects/umbrafox-workspace/umbrafox/obj-x86_64-pc-linux-gnu/dist/bin/umbrafox \
  --output /home/wyatt/.cache/codex/umbra-perf-20260926/local-off-1 \
  --profile off \
  --bus /tmp/codex/teamwork/umbra-perf-20260926/bus.txt
```

Repeat with a new output directory for A/A feasibility, then a separately labeled
`--profile on` capture. At startup the fixture waits for ownership verification
and before-snapshots. Warmup and trial phases have explicit fixture User Timing
marks. These marks are normal authored test-page content, not browser-added
production APIs. Correctness is deterministic JS/layout/canvas checksums, not a
compositor screenshot oracle. The host is concurrently used; short headless
captures validate tooling and attribution, not noise-calibrated release timings.

For a valid profile use a unique owned `profiler-cli` session, inspect metadata
and actual threads, restrict to matching `local-perf` phase intervals, then stop
only that session. Native symbols may be incomplete; do not guess missing names.

The [tool runbook](../../../tools/umbrafox/performance/README.md) includes export
and phase-analysis commands. The analyzer consumes `profiler-cli` exports, not
raw Firefox profile internals.
