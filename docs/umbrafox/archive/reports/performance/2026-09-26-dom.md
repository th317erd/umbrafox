## Observed Producer-to-Consumer Map

### 1. Task dispatch and DOM work

- `xpcom/threads/nsThread.cpp`, `nsThread::ProcessNextEvent`: main-thread work comes through `TaskController::GetRunnableForMTTask`; ordinary off-main-thread events use their event queue. Main-thread wrapper runnables deliberately do not emit duplicate Runnable markers because TaskController does that. Direct task draining and script observer callbacks also surround event execution; one Runnable marker is not a complete browser event-loop accounting model.
- `xpcom/threads/TaskController.cpp`, `AddTask` -> `RunTask`: `TaskController::AddTask` emits a flow marker, with a dispatch stack conditional on the Flows profiler feature. `Runnable` markers contain the task name, priority and pointer-derived flow identity; complete and incomplete task marker types differ. Correlate dispatch and execution on the owning process/thread, not names alone. A pointer-derived flow is not a permanent document identifier.
- DOM producer example: `dom/base/nsINode.cpp` insertion calls `MutationObservers::NotifyContentInserted`; `dom/base/Element.cpp` attribute changes call `MutationObservers::NotifyAttributeChanged`. `dom/base/MutationObservers.cpp` routes notifications through ancestor observers and PresShell. Removals notify PresShell before the old tree shape disappears; other changes notify it after the mutation. This internal notification mechanism is distinct from delivery of JavaScript MutationObserver callbacks.
- `layout/base/PresShell.cpp`, `ContentInserted`/`ContentAppended` -> `RestyleManager` and `nsCSSFrameConstructor` with asynchronous insertion; character-data and attribute/state paths have their own handlers. These changes may dirty style, reconstruct frames, trigger layout, or require no rendering work. Do not assume every mutation generates a paint.
- `dom/base/nsDOMMutationObserver.cpp`, `HandleMutationsInternal` -> `HandleMutation`: pending observer batches become callback records; stale/non-current inner windows clear records rather than invoke the callback. Callbacks can mutate again. Proposed instrumentation must not install a new page MutationObserver or change notification order just to count mutations.

### 2. Dirty style and scheduling

- `layout/base/PresShellInlines.h`: `SetNeedStyleFlush` sets the need flag, emits `SetNeedStyleFlush` with a non-native stack option and inner-window attribution, and captures `mStyleCause` when no cause is already retained. `SetNeedLayoutFlush` similarly stores `mReflowCause`. These are coalesced causes, not an exhaustive list of all contributing mutations.
- `PresShell::EnsureStyleFlush`/`EnsureLayoutFlush` -> `ScheduleFlush` schedules `RenderingPhase::Layout` through the refresh driver, except for destruction/BFCache-entry cases. The current checkout uses rendering phases; older descriptions of only a style-observer flush list are incomplete.
- `layout/base/nsRefreshDriver.cpp`, `Tick`: handles frozen/disconnected/old-timestamp cases, paint backpressure, coalesced input, rendering phases, animation callbacks, layout/ResizeObserver work, and paint. Markers include `RefreshDriverTick` with tick reasons and inner-window ID; `RefreshDriverTick waiting for paint`; first-contentful-paint/after-load waiting markers; `requestAnimationFrame callbacks`; and `requestVideoFrame callbacks`.
- `Tick` -> `Document::DetermineProximityToViewportAndNotifyResizeObservers` during the layout phase, followed later by the paint phase. Script callbacks, observer iterations, synchronous reads, suppression, and destruction mean the pipeline is not one linear task-to-one-frame transaction.

### 3. Flush, style traversal and reflow

- `dom/base/Element.cpp`, `GetBoundingClientRect` -> `GetPrimaryFrame(FlushType::Layout)` is a concrete forced-layout entry point. A layout request does not prove that dirty work existed or that a reflow actually ran.
- `PresShell::DoFlushPendingNotifications` emits `DoFlushPendingNotifications` with the flush-type text, captured stack and inner-window ID. It checks whether flushing is safe, handles external resources/media/font/animation updates, calls `RestyleManager::ProcessPendingRestyles`, and conditionally performs layout. It can return without the expected work if lifecycle/safety conditions fail.
- `layout/style/RestyleManager.cpp`, `ProcessPendingRestyles` -> `DoProcessPendingRestyles` -> `ServoStyleSet::StyleDocument`, post-traversal change hints, `ProcessRestyledFrames`, and frame construction/reflow/paint consequences. Restyle processing can repeat while new work is generated. Container-query and anchor-position updates also participate.
- `layout/base/AutoProfilerStyleMarker.h` produces `Styles`, with `elementsTraversed`, `elementsStyled`, `elementsMatched`, `stylesShared`, `stylesReused`, the retained cause, and inner-window ID. `servo/components/style/traversal.rs` produces per-thread counts; `servo/components/style/driver.rs` aggregates thread-local statistics and publishes them through `ServoTraversalStatistics::sSingleton` on the main thread. The main-thread Styles interval is elapsed flush time and the counts aggregate workers; neither is per-worker CPU time.
- `PresShell::DoReflow` emits a `Reflow` label and `Reflow (sync)` or `Reflow (interruptible)` tracing markers, using `mReflowCause` and the document's inner-window ID. `FrameNeedsReflow`/dirty-root coalescing is described in `layout/docs/LayoutOverview.md`. A DoReflow interval is a root reflow, not a count of every frame visited. Reflow schedules paint even before individual changed descendants schedule it again.
- Existing auxiliary markers include `UpdateContainerQueryStyles`, `UpdateAnchorPosLayout`, and frame-constructor labels such as `nsCSSFrameConstructor::ContentRangeInserted`. Labels require a sampling hit; marker counts and sampled-label hit counts are not interchangeable.

### 4. Invalidation, retained display lists and WR submission

- `layout/generic/nsIFrame.cpp`, `SchedulePaint` invalidates rendering observers and schedules painting, with a suppressed-paint early return. `nsRefreshDriver::SchedulePaint` retains `mPaintCause` and schedules the paint phase.
- `nsRefreshDriver::PaintIfNeeded` emits `ViewManagerFlush` with inner-window ID, retained paint cause and textual transaction ID. It forwards composition payloads to the window renderer and invokes synchronous painting. Throttled/suppressed/VR conditions can skip painting; Tick clears unconsumed composition payloads when no paint occurs.
- `layout/base/nsLayoutUtils.cpp`, `PaintFrame` produces `DisplayList`, `DisplayListResources`, and `PerfStats::Metric::DisplayListBuilding`; it tries `RetainedDisplayListBuilder::AttemptPartialUpdate`, merges partial results or rebuilds the whole list.
- `layout/painting/RetainedDisplayListBuilder.{h,cpp}` has `mNewItems`, `mRebuiltItems`, `mRemovedItems`, `mReusedItems`, `mTotalItems`, partial/full build durations, result (`Failed`, `NoChange`, `Updated`), and failure reason (`EmptyList`, `RebuildLimit`, `FrameType`, `Disabled`, `Content`, `VisibleRect`, `NA`). The merge path has a DisplayListMerging profiler category label. The observed consumer in `nsLayoutUtils.cpp` includes a diagnostic printf block under `#if 0`; do not describe that block as an enabled profile exporter. This is a candidate for exposing already-collected summary data, not justification for always-on new tree walks.
- `gfx/layers/wr/WebRenderLayerManager.cpp`, `EndTransactionWithoutLayer`: `WrDisplayList` wraps conversion via `WebRenderCommandBuilder::BuildWebRenderCommands`; `ForwardDPTransaction` covers serialization/forwarding. It creates transaction IDs, passes vsync/refresh/transaction timestamps, and records `WrDisplayListBuilding` duration. Empty transactions use a separate path and must not be omitted from future correlation tests.
- `gfx/layers/wr/WebRenderBridgeParent.cpp`, `RecvSetDisplayList`: consumes the submitted data, generates a WR epoch, processes the display list, and retains transaction/vsync/payload metadata. `SetDisplayList` is attributed using the root compositor bridge's inner-window ID; this is not proof of an exact OOP-iframe document attribution. `SceneBuiltNotification` emits `CONTENT_FULL_PAINT_TIME` and `gfx_content.full_paint_time` when scene-built notification reaches the compositor thread. That endpoint is not actual display presentation. No gfx/wr source was required for this lane; Rust renderer internals remain the graphics lane's responsibility.

### 5. Input delay, presentation and long tasks

- `dom/events/EventDispatcher.cpp` emits paired `DOMEvent` markers around event-target-chain handling when profiling is active. Payload includes event type, target description, latency and inner-window attribution. Latency is `dispatch start - event timestamp`, not handler duration or input-to-presentation delay. Synthetic events cannot stand in for native-input presentation measurements.
- The same function attaches composition payloads for trusted keypress/click events only under the observed pending-tick/root-context conditions; click sources are constrained. `nsRefreshDriver::PaintIfNeeded` forwards those payloads; WR transaction metadata carries them onward.
- `gfx/layers/ipc/CompositorBridgeParent.cpp`, `RecordCompositionPayloadsPresented` consumes payloads and a composition-end timestamp. It emits `<payload type> Payload Presented` and accumulates `performance_interaction.keypress_present_latency`, `performance_interaction.mouseup_click_present_latency`, and `gfx.scroll_present_latency`. Preserve the timestamp's actual endpoint; do not call it independently verified physical scanout. Payload capture/forwarding and metric accumulation are not entirely disabled when profiler markers are off.
- `xpcom/threads/nsThread.cpp`, `PerformanceCounterState::MaybeReportAccumulatedTime` emits `LongTask`/`LongIdleTask` with schema `MainThreadLongTask`; nested runnable accounting and idle classification matter. Runnable telemetry has a separate `MOZ_COLLECTING_RUNNABLE_TELEMETRY` gate. Internal long-task markers are not the web Long Tasks API and do not establish its availability.

### 6. Aggregate timings and retained memory

- `mozglue/misc/PerfStats.h` provides selective process metrics including `Styling`, `Reflowing`, `DisplayListBuilding`, `WrDisplayListBuilding`, `LayerTransactions`, `Rasterizing`, `FrameBuilding`, `Compositing`. This inventory verified the DOM/style/layout/DL/WR producers, not every graphics metric producer.
- `tools/performance/PerfStats.cpp`, `SetCollectionMask` propagates the mask to content/GPU processes. `CollectPerfStatsJSON` exports parent/content/GPU results, names, counts and aggregate time. Content IDs here are `ContentParent::ChildID`, not automatically OS PIDs; current URL lists are not full document-history attribution. Collection ignores some bridge-response failures, so a missing process result must not be treated as zero work or complete coverage. The consumer interface is existing `ChromeUtils` in `dom/chrome-webidl/ChromeUtils.webidl`, not a page API.
- `testing/raptor/browsertime/speedometer3.js` currently explicitly collects only `MinorGC`, `MajorGC`, `NonIdleMajorGC` with `commands.perfStats.start`. Running it unchanged does not automatically enable Styling/Reflowing PerfStats merely because those counters exist. Its manifest does include GeckoMain/Compositor/Renderer/TaskController/StyleThread profiler filters and `nomarkerstacks`, so a separate cause-stack run needs a deliberate profiler configuration change.
- `dom/base/nsWindowMemoryReporter.cpp` obtains window sizes and emits `explicit/window-objects/...` paths classified as active/cached/detached/ghost, DOM node/event-target/ResizeObserver sizes, retained `/layout/display-list`, `/layout/pres-shell`, stylesheets/style sets/invalidation maps/computed values/frame properties. JS reporting consumes the window-path mapping too. Keep memory-report process identity as well as window identity.
- `ghost-windows` is an existing count. Detection uses detached-window weak references, browsing-context-group criteria and a timeout/minimization boundary. Same-group detached windows and legitimate caches complicate interpretation. A nonzero count or one post-close memory snapshot is not proof of a leak.
- `testing/awsy/awsy/test_memory_usage.py` consumes memory checkpoints: Start/StartSettled, TabsOpen/TabsOpenSettled/TabsOpenForceGC, TabsClosed/TabsClosedSettled/TabsClosedForceGC. These are useful phase boundaries, but a forced-GC result does not represent normal browsing retention by itself.

## Attribution Rules

Preserve `(process type, OS pid, thread id/name, innerWindowID, embedderInnerWindowID, tabID)` where available; keep PerfStats child IDs separately typed. Main-thread DOM/layout work occurs in the document's process; parent chrome and each content process have distinct GeckoMain threads. Style worker work needs its own samples rather than attributing all Styles duration to main-thread CPU. Compositor/WR work may reside in GPU or parent fallback processes, which must be recorded rather than assumed.

Keep task flow IDs, refresh/vsync IDs, WR pipeline/epoch and transaction IDs in their own namespaces. A transaction can coalesce many mutations; a task can touch several documents; a document can span several frames and navigations. Marker overlap alone does not establish causation. Use existing multiprocess/page metadata tests as schema checks and add an explicit cross-origin OOP-frame workload before claiming the joins work.

## Observed Overhead Gates and Limits

| Existing mechanism | Disabled-path observation | Enabled-path observation / caveat |
| --- | --- | --- |
| TaskController RunTask | Direct Run when markers are not being collected; compile alternative exists when its profiler implementation is absent | Name lookup, timestamps, labels, markers and flows; dispatch stack depends on Flows |
| Styles wrapper | Returns without setting singleton/timestamp when this thread is not profiled for markers | Singleton enables aggregate publication; timestamps, counts, cause serialization |
| Servo statistics | `elements_traversed` and sharing/matching counters increment in inspected traversal code without a profiler-active branch | Aggregation is conditional on reporting/dumping; do not infer that disabled collection removes per-element bookkeeping |
| Cause stacks | `profiler_capture_backtrace` returns before buffer allocation if inactive or `nomarkerstacks` | Otherwise buffer allocation, stack capture and copy; coalesced cause storage can retain profile buffers until flush |
| DOMEvent | Additional event wrapper/type/target/timing work is inside `profiler_is_active()` | That gate is broader than thread-selected marker collection; active-but-filtered/paused states need their own audit |
| PerfStats | Collection mask initially zero; RAII reads mask and skips clock when disabled | Clocks and aggregate recording when selected; process collection/serialization adds work |
| Retained DL metrics | Counters and StartBuild/Elapsed timers exist outside a profiler-only gate in inspected paths | Diagnostic double-build mode intentionally does extra work and is not a neutral performance baseline |
| Composition payloads | Trusted-event payload logic and Glean accumulation can occur without marker collection | Markers add payload-name/text formatting; not a universal input census |
| Memory reporters | Snapshot collection is a distinct operation, not a free continuous counter | Snapshot walks, GC/CC/minimization and logging can perturb retention/timing; measure outside latency windows |

New probe review must cover argument evaluation before marker functions, not just marker-buffer writes. `PROFILER_MARKER` forwards arguments to a function; putting an allocation or subtree count into those arguments is not evidence of a zero-cost disabled path. These source observations motivate measurement; no overhead magnitude was measured here.

## Six Prioritized Workload and Instrumentation Gaps

### P1. Forced Layout Versus Batched Writes

**Hypothesis:** a workload's repeated geometry reads may cause more synchronous dirty flushes than the same mutations followed by one read. The source establishes the possibility, not a problem in current browsing.

**Workload:** fixed seeded DOM sizes, same mutations in (a) write/read interleaving, (b) all writes then one geometry read, (c) repeated read-only controls, (d) detached/display-none controls. Verify identical final geometry and relevant event/observer ordering; include resize-callback reentrancy and navigation/destruction.

**Reuse/proposed gap:** existing `DoFlushPendingNotifications`, `Styles`, `Reflow (sync)`, cause stacks and PerfStats first. If insufficient, add one opt-in flush-summary marker with requested flush type, actual style/reflow execution counts, dirty-root counts, document identity, and a scoped flush sequence; no per-frame clocks in the default path.

**Gate and next falsifier:** compare sync-reflow counts and exclusive durations after subtracting nested marker overlap, across the control cases. Reject the hypothesis if there is no reproducible excess actual reflow or if JS/other work explains the latency. Run geometry correctness WPT and new off/on summary tests before an optimization. Existing GetBoundingRect WPT tests geometry, not flush frequency.

### P2. Mutation Batches and Observer/Microtask Boundaries

**Hypothesis:** style/reflow work differs materially across mutation batching strategies or observer-driven re-mutations.

**Workload:** identical N insertions/attribute/text changes in a fragment, one task, multiple tasks, and a callback-induced second batch. Include zero-observer control, several observers, disconnect/reobserve, adoption/removal and old-inner-window teardown. Do not modify delivery semantics to improve the score.

**Reuse/proposed gap:** source notifications -> PresShell -> Styles counts exist, but no verified end-to-end mutation-batch ID here. Propose bounded per-document summary counters at existing notification/delivery boundaries (`mutation count`, `observer delivery count`, `records delivered`, `flush count`) joined to the task/flush sequence. Count at existing visits; do not walk the DOM or retain node references. Callback records are not necessarily one-to-one with mutations.

**Gate and next falsifier:** same final DOM plus unchanged callback records/order; compare normalized mutations, deliveries and actual flushes. Falsify a batching explanation if callback/flush counts agree and the measured difference is elsewhere. MutationObserver WPT callback-tricky and childList tests are existing correctness controls, not throughput tests. Dromaeo DOM provides a broader comparison, not this precise batch attribution.

### P3. Style/Paint Invalidation Fan-Out and Retained DL Fallbacks

**Hypothesis:** a small edit may cause unexpectedly broad traversal or a full retained-DL fallback in a representative workload.

**Workload:** local class/attribute/text change versus ancestor/sibling-selector changes; constrained selectors versus `:has()`/inherited style where applicable; paint-only color versus geometry-changing dimensions; stacking contexts, frame creation/deletion, scroll/transform, stable no-change control. Keep rendered output constant between implementation variants, not between intentionally different workload cases.

**Reuse/proposed gap:** Styles traversal/sharing counts, DL duration and existing retained metrics. Propose a gated `RetainedDisplayListSummary` emitted once per build containing existing result/reason/counts/durations and typed document/transaction association. Optional sampled invalidation-reason summaries must be separately costly-probe gated; do not export selectors or target text by default.

**Gate and next falsifier:** repeat seeded workloads; correlate actual fail reasons/item rebuild counts with time, then change only one causal factor. Reject a fallback hypothesis when the count/reason remains unchanged or the cost is in WR/GPU after submission. Use retained-DL reftests for pixels and StyleBench for broader style behavior. Preserve manifest expected failures/skips; the current retained-DL suite is implementation-specific, so new interoperable geometry/paint semantics tests should go to WPT per layout/AGENTS.

### P4. Cross-Origin Iframe Scheduling and Presentation Attribution

**Hypothesis:** OOP-frame handoffs or paint throttling account for a measured end-to-end gap that is invisible in a single main-thread view.

**Workload:** same-origin frame, cross-origin frame under normal site isolation, then simultaneous parent/child mutation and resize/input; navigate or remove the child while work is pending. Use deterministic locally hosted test origins and explicit handshake IDs in test fixtures, not production page injection. Confirm actual child process IDs instead of inferring OOP solely from origin.

**Reuse/proposed gap:** profile page metadata, IPC markers, ViewManagerFlush and WR transactions. Propose an internal mapping record for `(innerWindowID, pipelineId, epoch, transactionId, vsyncId)` at genuine producer/consumer boundaries if current data cannot support the join. Reuse existing metadata before changing IPC; any new transport fields must be diagnostic-build-only and must not affect production scheduling.

**Gate and next falsifier:** compare queue/dispatch/refresh/submit/presentation endpoints for each process; attribute missing/dropped/coalesced work explicitly. Falsify the handoff hypothesis if the gap is in one document's CPU work or GPU time rather than the boundary. Existing profile_fission tests verify process/private/container metadata; multi_frame_page_info uses same-origin embedding. Neither alone proves cross-origin per-frame transaction attribution. Add that focused test and teardown/stale-ID cases.

### P5. Long Tasks, Input Delay and Input-to-Presentation

**Hypothesis:** a chosen page's input delay is dominated by a long runnable, microtask chain, or layout work rather than compositor/presentation delay.

**Workload:** controlled CPU task versus mutation/reflow task versus Promise/MutationObserver chain, each with real harness-generated trusted input and an observable paint; compare idle/no-paint and APZ-only cases. Include background/hidden tab controls without changing Firefox's throttling defaults.

**Reuse/proposed gap:** Runnable flows, `LongTask`/`LongIdleTask`, `DOMEvent`, refresh/backpressure markers, composition-payload markers and latency metrics. Only add a bounded internal input/transaction correlation summary if these cannot disambiguate stages. Keep dropped/no-paint endpoints, not only successfully presented events.

**Gate and next falsifier:** separate queue wait, handler duration, rendering delay and compositor endpoint. A long task occurring nearby is not the cause until timing and controlled removal explain the delay. Falsify main-thread causation if dispatch is prompt and the delay starts after submission. The existing parent-process marker test dispatches a synthetic DOM event and checks a positive latency; it is not a native-input latency benchmark. Long-task WPT metadata has `implementation-status: backlog` and expected FAIL cases; do not turn on/add a web API as an instrumentation workaround.

### P6. Retained Document and Display-List Memory After Teardown

**Hypothesis:** retained DOM/style/display-list allocations grow across repeated document lifecycles beyond expected BFCache and live-reference retention.

**Workload:** repeated open/mutate/close and iframe detach/adopt cycles; intentional retained-reference control versus released-reference case; normal BFCache navigation versus non-cacheable test case; process reuse and process-exit cases. Snapshot at settled-before, after close, after idle, and separately after explicit GC/CC/minimization. Keep profiler buffer size and profile-object lifetime fixed.

**Reuse/proposed gap:** existing window memory paths, ghost count, GCSlice/CCSlice and AWSY phases. Prefer these to new accounting. If attribution remains inadequate, add diagnostic-only lifecycle summaries with non-owning numeric document IDs, allocation-family counts and collection epochs. Never keep Document/Node/Window references alive to measure their death; separately measure the probe's own retention.

**Gate and next falsifier:** require repeated-cycle retained-byte slope and live-object evidence after documented settling, not RSS alone or one ghost count. Reject a leak hypothesis if growth plateaus as expected or is explained by BFCache, allocator retention, deliberate references, profile buffers, or live process state. Add regression tests for dropped references and probe teardown; GC/CC marker presence only verifies recording, not leak freedom.

## Durable Probe Acceptance Contract (Proposed, Not Implemented)

1. Leave reviewed instrumentation and regression tests in tree. New expensive per-node/selector/stack/lifetime probes require an explicit diagnostic build gate that is absent in production/release builds, plus an internal opt-in defaulting OFF in diagnostic builds. A profiler-enabled release build alone is not a sufficient costly-probe gate. Exact new flag/pref names need design review; none is claimed to exist.
2. Reuse existing summaries and typed numeric identifiers. Branch before clocks, argument construction, strings, allocations, stacks, TLS setup, IPC and subtree walks. Use bounded/thread-local counters and bounded summaries; avoid new shared atomics per node. Overflow must be visible internally and must never backpressure rendering. Do not silently sample one thread/process differently without recording the configuration.
3. Gate schema registration, payload storage, object fields and destructors consistently so compiled-out builds do not carry costly work or changed hot-structure layout. Verify generated objects/disassembly and symbols in a later authorized build; source `#ifdef` inspection alone is insufficient.
4. Add focused tests for release-gate absence, diagnostic runtime-off behavior, enabled known counts, inactive/paused/filtered profiler, start/stop while a flush is open, buffer exhaustion, reentrancy/nested tasks, same/cross-origin frames, document teardown/BFCache, and thread shutdown. Use side-effecting test argument factories to prove disabled wrappers do not evaluate expensive arguments. Tests must show no retained document references and no stale cross-navigation IDs.
5. Default fast-path tests must check absence of extra records/allocations/clocks/IPC where promised, then compare page-visible geometry, mutation/resize event order, task/microtask order and existing API shapes to the matching Firefox baseline. Never add page globals, DOM attributes, custom events, PerformanceObserver entry types, WebIDL, network headers or userland timing hooks. Privileged profiler/memory consumers only. Private browsing/container contexts need non-content-leaking identity handling.
6. Benchmark separate states: matched baseline; release with costly probes compiled out; diagnostic build with opt-in OFF and profiler inactive; opt-in OFF with profiler active/filtered/paused; opt-in ON with summaries; opt-in ON with expensive stacks/details. Hold prototype OFF throughout. Use randomized paired runs, fixed workload seed, browser revision/build flags/platform/renderer/process configuration, and report distributions/confidence intervals plus marker volume, allocations and CPU/RSS. Agree a non-regression/noise budget before results; no universal percentage is justified by this inventory.
7. Enabled diagnostic measurements may perturb timing. Keep a low-overhead run for scores and a separate detailed causal run. Profiling must not reorder tasks, bypass flush safety, force layouts, disable isolation, alter throttling, or change page API support. Default Firefox parity is mandatory; generic rule-bending is not an exception.
