# Sustained Playback Preparation And First Capture

> **Archived project record.** This page preserves dated project evidence and its original status. Source, tests, and current Umbrafox documentation outrank it.

## Outcome

A new bounded playback fixture and pinned synthetic clip now exercise a minute
of continuous media. One isolated, headless laptop capture completed all 31
samples with clean owned-browser termination. The overall driver nevertheless
exited 1: its unchanged, strict package-tree check found an extra `.parentlock`
in the disposable test installation. This failure is retained, not waived.

The recorded 1,812 frame increments and zero dropped-frame increments are a
single headless integration observation, not evidence of GPU smoothness,
physical presentation, a speedup, or a YouTube fix. No further browser was
launched after the package-check failure. Headed-window permission remains
pending; the owner's browser, personal profiles, installed build and launcher
were not changed.

## Package-Check Failure

The shared disposable baseline installation acquired a zero-byte `.parentlock`
at 01:26:59.774 UTC, mode 0664, owner UID 1000. All original 46 files still have
their expected hashes, sizes and modes; a separate audit verifies the exact
47-entry tree including that recorded extra file. The original 46-entry guard
still fails, and neither its manifest nor implementation was relaxed. The lock
was not deleted. Other original inputs/evidence remain unchanged.

An upstream source route supports a plausible explanation:

- `UpdateService.hasUpdateMutex` calls the update mutex's `tryLock`.
  [Pinned source](https://searchfox.org/firefox-main/rev/d0f18859d99ecb16f4c5d641b35a5f3bdb7b4f36/toolkit/mozapps/update/UpdateService.sys.mjs#569)
- `UpdateMutexImpl::TryLock` obtains `XRE_UPDATE_ROOT_DIR` and uses
  `nsProfileLock` there.
  [Pinned source](https://searchfox.org/firefox-main/rev/d0f18859d99ecb16f4c5d641b35a5f3bdb7b4f36/toolkit/xre/nsUpdateMutex.cpp#15)
- `GetUpdateRootDir` returns the executable parent on Linux, and
  `nsProfileLock::LockWithFcntl` creates/truncates a lock file.
  [Directory producer](https://searchfox.org/firefox-main/rev/d0f18859d99ecb16f4c5d641b35a5f3bdb7b4f36/toolkit/xre/nsXREDirProvider.cpp#949)
  [File producer](https://searchfox.org/firefox-main/rev/d0f18859d99ecb16f4c5d641b35a5f3bdb7b4f36/toolkit/profile/nsProfileLock.cpp#193)

This is a source-backed hypothesis, not a captured writer stack, proof of a new
profile, or proof of the exact loaded source path. No update was observed, and
no absence of update/network activity is inferred. Searchfox CLI 0.18.0 reports
0.20.4 available; no tool installation/update was performed.

The inner `run.json` says pass because local workload capture and cleanup
finished. The outer driver failed during its subsequent tree verification.
Both statuses must be retained; the offline audit explicitly says
`functional-evidence-pass`, not overall success.
