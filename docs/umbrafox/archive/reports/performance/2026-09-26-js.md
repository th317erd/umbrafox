### GC and Allocation

**Observed locally:** `xpcom/base/CycleCollectedJSRuntime.cpp::GCSliceCallback` converts `JS::GCDescription` to profiler `GCSlice` and `GCMajor`; `GCNurseryCollectionCallback` converts `JS::MinorGcToJSON` into `GCMinor`. JSON formatting is gated by `profiler_thread_is_being_profiled_for_markers`. The nursery callback still takes timestamps and records `PerfStats::Metric::MinorGC` outside that profiler gate; disabled marker recording is not zero total GC-accounting overhead.

`js/src/gc/Statistics.cpp` serializes `max_pause`, `total_time`, `reason`, `slices`, `mmu_20ms`, `mmu_50ms`, `nonincremental_reason`, `post_heap_size`, malloc heap sizes, collection numbers, and per-slice `pause`, `budget`, states, and phase timings. `js/src/gc/Nursery.cpp` serializes `bytes_tenured`, `cells_tenured`, `bytes_used`, capacity changes and nursery phase timings; fields can be conditional. Major/pause values are milliseconds; nursery phase values are microseconds. Verify schema/units per capture.

`GCMajor` spans an incremental cycle, not continuous main-thread blocking. Sum individual slice blocking with proper thread/time overlap handling; never sum the enclosing major interval as pause time. `GCSlice` and `GCMinor` are the relevant pause intervals. Parallel marking also has `Parallel marking ran`, `Parallel marking wait`, and donated-work/failure events in `gc/ParallelMarking.cpp`.

Allocation recording is separately enabled in `ApplyJSSamplingChange` via `JS::EnableRecordingAllocations(..., 0.01)`. This is sampled JS allocation data, not exact allocation totals or a native-retention census. `profiler-cli --strategy js-allocations` is only meaningful if the selected thread has those data. Use allocation recording in a dedicated diagnostic configuration and measure its overhead.

`Statistics` supports `MOZ_GCTIMER`, `JS_GC_PROFILE`, `JS_GC_PROFILE_FILE`, and `JS_GC_BUFFER_STATS`. Logging is useful for focused diagnosis, not a substitute for uninstrumented performance measurement.

### Event Loop, Tasks, and Microtasks

### Long-Lived Stress Protocol

Proposed initial run: 10-minute warmup followed by 120 minutes of fixed, seeded 5-minute cycles, with a hard 150-minute deadline and per-action watchdogs. Keep the same browser session alive through measured cycles; record process IDs/restarts so hidden resets cannot masquerade as stable retention. Each cycle has editing/list updates, bounded promises and worker messages, tab navigation/back/forward, DOM/listener teardown, and a fixed 30-second idle segment. A separate recovery endpoint closes test tabs/workers and observes another fixed idle window without forcing GC in the timed production-behavior run.

Capture unprofiled throughput and input/tail latency per cycle, process CPU/RSS and available privileged heap summaries, GC minor/slice pause distributions, post-GC heap trajectory, CC visited/freed/suspected trends, task completion backlog, and failures/timeouts. Do not equate RSS with JS heap. Keep diagnostic profiles in bounded, predeclared windows (e.g. early/middle/late) in a separate run; rewarm after profiler state changes. Allocation/IR/spew gets its own short run, not two hours of unbounded output.

Separate deterministic test failures, disk/memory-pressure aborts, thermal throttling, and crash/restart outcomes from timing samples. No infinite microtask starvation loop. Data-dependent self-extending queues require a maximum count/time budget. Natural GC behavior is primary; explicit forced-GC/CC collection may be a separate diagnostic to distinguish retained objects from reclamation scheduling, never silently part of the score.

Use predeclared paired/randomized run order, identical workload revisions and payload hashes, and independent run-level statistics. Start with five runs/configuration where practical, increase at a predeclared checkpoint up to 20 under the skill protocol; report effect size, uncertainty, raw distributions and tail metrics. Do not repeatedly inspect significance until a favorable p-value appears, count loop iterations as independent runs, or accept a score gain smaller than the calibrated noise/observer budget. Long-soak replication may need a separate explicitly approved budget; one soak is feasibility evidence only.
